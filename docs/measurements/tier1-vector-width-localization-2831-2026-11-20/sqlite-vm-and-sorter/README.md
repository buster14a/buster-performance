# Two hoisted constants in SQLite’s virtual machine

On Buster `c8b259413110b1d6f5ff9a005a1c49f48ca01e57`, the SQLite sorter vectorizes its integer product `nDiv *= 16`, starting at one, for `i = 1; i < nDepth; i++`. The scalar IR records the loop bound from the second parameter, the induction step of one and integer multiplication by sixteen. The vector IR splats sixteen and one, multiplies per lane, then reduces the lanes by multiplication. [Scalar IR](sorter-before.ir) and [vector IR](sorter-after.ir)

After inlining, the two vector constants move from block 2,194 of `sqlite3VdbeExec` to block 21 of the rebuilt CFG. They are live across calls in the main VM dispatch. The ordinary 64-byte vectorized compiler emits a 118,847-byte VM, up from 91,580 bytes with default passes. In a private diagnostic the compiler completed LICM, then retained the entering order only for this VM. With the vectorized loop still present, its size dropped to 92,553 bytes and its frame from 1,160 to 1,032 bytes. The emitter reported 1,743 versus 571 call stores and 1,846 versus 674 call loads. Disassembly shows 2,344 extra `vmovdqu32` and four extra `movaps` instructions when motion is applied. Ordinary spill counts are identical in this pair. The 16- and 32-byte runs have the same increase in call saves and reloads. The unmodified and no-intervention diagnostic compilers agree on the complete original objects. SQLite 3.53.2 computes the depth from a signed 32-bit number of sorted runs, with fanout 16 and a 64-bit divisor. At `INT_MAX` the depth is seven, so this product executes at most six scalar iterations. The vector bodies for eight and sixteen i32 lanes are unreachable through the upstream caller. A four-lane body can be reached in principle for more than 1,048,576 initial runs. The [depth witness](tree-depth-bounds.tsv) covers both sides of every power-of-sixteen transition, and the [witness C](depth.c) contains the upstream calculation.

The sort harness verifies the id, numeric key and all 96 payload bytes of each row, with an independent Clang build. At 4,096, 32,768 and 131,072 rows in memory, the sorter-tree helper was never entered. With file-backed temp storage, 512-byte pages and `PMASZ=1`, the observed depths were one, two and three across 16, 128 and 512 calls. Eighteen independent GDB runs at three vector caps confirmed zero entries into the actual VM vector multiply for these inputs. All 138 initial program/input comparisons matched, as did the additional two diagnostic variants in the timing run. The 1,176 local Ryzen 9 7940HS process measurements cover seven compilers or diagnostic settings, four placements, three row counts and two temp-store modes. Six paired comparisons follow a warm-up in each setting. Permitting only the sorter to vectorize increased retired instructions by 1.22–1.42% for in-memory sorts and 0.80–1.10% for spill sorts. Keeping its original VM order reduced the difference to below 0.003% in every setting. Paired cycle changes depend on layout. At all twelve spill settings the isolated sorter added 0.32–4.40% cycles, while its memory settings ranged from −1.96% to +5.77%. Runtime data are local; direct 9700X confirmation remains pending.
